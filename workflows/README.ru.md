# Сценарии для агента

[English](README.md) · **Русский**

Скрипты для инструмента `Workflow` в Claude Code. Они необязательны, и их
сознательно мало: сценарий оправдан там, где работа — это **суждение или целый
конвейер**, а не там, где это запрос к данным.

Распараллеливать запросы агентами — неправильное лечение. Поиск по репозиторию
для каждого элемента схемы занимал около минуты, если звать по одному; ответом
стал не веер агентов, а `dochub_search_components`, принимающий список
запросов: одна сборка манифеста на всех, секунда вместо минуты,
детерминированно и в любом MCP-клиенте, а не только в Claude Code.

## dochub-batch

Несколько схем разом: по агенту на схему — бриф, черновик, проверка,
регистрация — и отчёт, сгруппированный по решениям, а не по схемам: один и тот
же вопрос к пяти схемам задаётся один раз.

```
Workflow(name: "dochub-batch", args: {
  schemas: ["C:/schemas/a.drawio", "C:/schemas/b.drawio"],
  out: "C:/drafts"
})
```

Чтобы дошло до merge request, у схемы должно быть известно место в
репозитории — тогда вместо строки передаётся объект:

```
Workflow(name: "dochub-batch", args: {
  schemas: [{
    schema: "C:/schemas/a.drawio",
    yaml:   "<репозиторий>/architecture/domain/sales/orders/orderFlow.yaml",
    domain: "sales", context: "orders", subdomain: "orderFlow",
    own_root: "dotnet.orderService"
  }],
  publish: true
})
```

`publish` работает только при включённом `automode`: без него
`dochub_publish` откажется публиковать без подтверждения человека, и этот
отказ попадёт в отчёт как причина пропуска.

**Чтение идёт веером, запись — нет.** Черновики собираются параллельно, но
репозиторий один на всех: две ветки одновременно не завести, поэтому
регистрация и публикация идут по одной схеме за раз.

В отчёте отдельным списком — **какие поддомены затронуты**: свои и чужие. План,
задевающий чужой поддомен, останавливает эту схему и называет его поимённо:
правка чужого файла — это чужая ответственность и чужое ревью, и решение о ней
принимает человек, а не фоновый агент.

## Когда их запускать

Спрашивайте у агента или ждите, что он предложит сам: скилл велит ему сказать
про готовые сценарии, когда задача на них похожа, и **спросить разрешения** —
сценарий поднимает несколько агентов, это заметные деньги и время. Одна схема с
согласованием сценария не требует.

## dochub-mr-review

Ревью чужого merge request в арх.репозитории: что меняет ветка, дальше по
агенту на файл — ссылочная целостность, регистрация, владение компонентами,
именование по накопленным правилам, — и каждая находка проверяется вторым,
скептически настроенным агентом. В отчёт попадает только то, что устояло.

```
Workflow(name: "dochub-mr-review", args: {
  base: "origin/main",
  head: "feature/orders",
  mr:   "<ссылка на merge request>"       # необязательно, для отчёта
})
```

Вкусовщина вне области: бизнес-названия и то, как автор разбил схему на
контексты, — его решения, а замечание, которое не подтверждает ни один
инструмент, это мнение, а не находка.

## Установка

Инструмент `Workflow` читает сценарии из `~/.claude/workflows/`:

```bash
cp workflows/*.js ~/.claude/workflows/
```

MCP-сервер должен быть подключён к сессии: субагенты находят его инструменты
через `ToolSearch`. Если сервер не подключён, прогон останавливается и говорит
об этом, а не выдумывает ответ.

## Что сознательно не сценарий

Цикл согласования — превью, замечания, правки — остаётся в основном диалоге.
Сценарий идёт в фоне и не может задать вопрос по ходу, а весь смысл этого
цикла именно в диалоге.
