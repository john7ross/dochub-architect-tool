# Архитектура

[English](ARCHITECTURE.md) · **Русский**

## Идея

Перенос схемы в репозиторий DocHub делится на два вида работы.

**Детерминированная** — разбор файлов, сборка манифеста, поиск существующих
компонентов, проверка ссылочной целостности, рендеринг, запись YAML, git. Это
код: повторяемо, проверяемо тестами и ничего не стоит выполнить.

**Смысловая** — решить, что `OrderHandlerService` реализует «обогащение и
отправку заказов контрагентам», что очередь принадлежит поддомену шины
событий, что вот эти пять связей образуют один сценарий. В схеме этого нет,
это приходит от человека, а агент помогает сформулировать.

Поэтому инструмент сделан MCP-сервером: первую работу он отдаёт инструментами,
вторую делает агент в диалоге с пользователем.

## Технологии

| Область | Выбор | Почему |
|---------|-------|--------|
| Протокол | MCP через stdio, FastMCP | клиент запускает сервер подпроцессом; не нужны порты и авторизация |
| Валидация | Pydantic v2 | схемы выводятся из моделей, клиент видит параметры |
| Разбор DrawIO | `xml.etree` из стандартной библиотеки | формат — обычный XML, внешний парсер ничего не добавляет |
| Рендеринг DocHub | JSONata поверх вендоренной метамодели | исполняем правила самого DocHub, а не переписываем их |
| Рендеринг диаграмм | PlantUML во вложенном jar | работает офлайн; раскладка ELK подключается отдельными jar-файлами |
| Оригинал DrawIO | вендоренный `viewer-static.min.js` | движок самого drawio: пользователь видит оригинал, а не реконструкцию |
| Правка YAML | ruamel.yaml | сохраняет комментарии и порядок ключей в файлах, которые читают люди |
| Чтение YAML | PyYAML | быстрее там, где оформление не важно |
| git | CLI `git` через `subprocess` | на одну зависимость меньше при раздаче архивом |
| GitLab | httpx | через API создаётся только merge request |

## Компоненты

Диаграмма: [docs/diagrams/component.png](docs/diagrams/component.png),
исходник [component.puml](docs/diagrams/component.puml).

### Точка входа

`app/mcp_server.py` — 20 инструментов. Только проверяет параметры, зовёт ядро
и оформляет ответ; логика лежит в модулях ниже. У одного инструмента своего
модуля нет: `dochub_brief` — это сборка, он зовёт парсеры, доменную схему,
манифест и накопленные правила и превращает всё, чего в них не нашлось, в
вопросы пользователю.

### Настройки

- `settings.py` — вся настройка установки: пути, умолчания для GitLab и
  `automode`. Три источника в жёстком порядке — переменная окружения, затем
  `.env`, затем пути, сохранённые через `dochub_workspace`, — и каждое
  значение помнит, откуда пришло: иначе «работает не с тем репозиторием» не
  диагностируется. Разбор `.env` свой: библиотека ради двадцати строк — это
  ещё одна зависимость впустую.
- `workspace.py` — пути, сохранённые агентом в прошлых сессиях. Остаётся
  источником с наименьшим приоритетом, чтобы уже настроенная через инструмент
  установка продолжала работать. Ищется по `DOCHUB_WORKSPACE`, затем
  `dochub-workspace.yaml` рядом с проектом, затем `~/.dochub/workspace.yaml`.
- `utils/paths.py` — расположение вложенных ресурсов, отсчитывается от кода, а
  не от рабочей директории: MCP-сервер запускается из произвольного каталога.
- `utils/logger.py` — логи в stderr; в stdout идёт протокол MCP.

### Разбор

- `parsers/drawio_parser.py` — C4-атрибуты на `<object>`, геометрическая
  вложенность, сжатые страницы, привязка к страницам.
- `parsers/plantuml_parser.py` — макросы C4.
- `parsers/base_parser.py` — общая модель: компонент, связь, результат разбора
  с выборкой по страницам.
- `parsers/ddd_parser.py` — доменная схема компании: домены, ограниченные
  контексты, поддомены, ответственные.
- `parsers/geometry.py` — вложенность по координатам, общая для обоих
  разборщиков DrawIO.
- `parsers/diagram_kind.py` — отличает физическую диаграмму от логической.

### Модель

- `transformer.py` — черновик: id из `c4Name`, уровни L2/L3 из вложенности,
  связи в `uml.$after` и разделение на свои и чужие компоненты.
- `reconcile.py` — сверяет схему с исходным кодом сервиса и показывает
  расхождения с файлом и строкой.

### Репозиторий

- `dochub/manifest.py` — разворачивает `imports` рекурсивно; без этого ссылки
  на соседние файлы не разрешаются.
- `dochub/native_renderer.py` — исполняет метамодель DocHub из `vendor/dochub`.
- `dochub/registration.py` — проверяет подключение файла к дереву.
- `dochub/registrar.py` — пишет в общие и чужие файлы; указатель владельцев
  отвечает на вопрос «чей это компонент».
- `publisher.py` — репозиторий через git CLI: состояние до работы (доступен ли
  origin, насколько отстали, что не закоммичено), обновление fast-forward,
  рабочая ветка — и дальше ветка, коммит, push и merge request с
  ответственным, ревьюверами и параметрами слияния. Каждый вызов git закрывает
  дочернему процессу stdin: под MCP stdin сервера — это труба протокола, и
  унаследовавший её процесс не завершается.
- `knowledge.py` — правила, подтверждённые на прошлых схемах.

### Превью

- `preview/renderer.py` — рендерит PlantUML, с офлайн-откатом, когда внешние
  подключения недоступны.
- `preview/server.py` — локальный HTTP-сервер; страница возвращает отрисованный
  оригинал обратно, за счёт чего картинка получается без сторонних программ.
- `core/drawio_export.py` — выгрузка схемы DrawIO в PNG или PDF через Draw.io
  Desktop. Нужна только когда SVG недостаточно: SVG даёт вендоренный движок, и
  для него ничего устанавливать не требуется.

## Два представления

**Логическое.** Агент ведёт последовательность: прочитать накопленные правила,
задать недостающие вопросы, проверить вид диаграммы, выбрать место в доменной
модели, сверить с кодом, построить черновик, показать превью, отработать
замечания, подключить к дереву, опубликовать, записать выученное. Диаграмма
последовательности [docs/diagrams/flow.png](docs/diagrams/flow.png) показывает
это целиком.

**Физическое.** MCP-клиент запускает `python -m app.mcp_server` подпроцессом и
общается через stdin/stdout. Сервер вызывает `java -jar lib/plantuml.jar` для
рендеринга и `git` для публикации, а для превью поднимает локальный HTTP-сервер,
который пользователь открывает в браузере. Всё, кроме API GitLab, работает на
машине; сеть после установки не нужна.

## Решения, которые стоит знать

**Рендеринг вендоренной метамоделью, а не своими правилами.** Самописный
генератор давал правдоподобную, но другую картинку. Метамодель из плагина
DocHub даёт вложенные области и аспекты внутри блоков — ровно то, что
показывает DocHub.

**Оригинал DrawIO никогда не пересобирается.** Человек сравнивает исходник с
результатом, значит слева должен быть исходник. Его рисует вендоренный
просмотрщик; реконструкция из распознанных компонентов была бы другой
картинкой и обессмыслила бы сравнение.

**Недоступные внешние подключения не ломают рендер.** Корпоративные схемы
тянут стили и иконки с внутренних серверов. Когда их нет, рендер повторяется
без них, а в ответе сказано, что структура верна, а оформление не применено.

**Компонент принадлежит владельцу.** Очереди, методы чужих API и хранимые
процедуры описываются в файле владеющего поддомена, даже если заведены под наш
сервис. Свой файл только ссылается на них по полному идентификатору.

**Публикация требует явного подтверждения.** Это единственный инструмент,
который меняет состояние и выходит наружу; без флага подтверждения он
отказывается работать и велит сначала показать превью.
