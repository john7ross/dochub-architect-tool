# Использование

[English](USAGE.md) · **Русский**

Сервер отдаёт 20 инструментов. Состояние меняют два — синхронизация
репозитория и публикация, остальные на чтение.

## Порядок работы

Скилл в `skills/dochub-architect/` задаёт порядок, которому следует агент.
Коротко:

1. прочитать настройки и накопленные правила, спросить недостающее;
2. синхронизировать репозиторий: доступен ли, не отстал ли, завести ветку;
3. собрать бриф — исследование идёт до вопросов, спрашивается только то,
   чего нет ни в схеме, ни в репозитории, ни в правилах;
4. убедиться, что диаграмма физическая и в нотации C4;
5. если дали исходники — сверить схему с кодом;
6. построить черновик, поискать компоненты для переиспользования;
7. показать превью и отработать замечания;
8. подключить файл к дереву и к файлам владельцев;
9. опубликовать после явного подтверждения;
10. записать выученное.

## Инструменты

### Настройки и знания

**`dochub_workspace`** — всё, чем настроена установка: пути, которые не
меняются от задачи к задаче, умолчания для GitLab (ветка назначения, шаблон
коммита, параметры merge request) и включён ли `automode`. Показывает и то,
откуда взято каждое значение — из `.env`, из переменной окружения или из
сохранённых путей, — и чего ещё не хватает.

**`dochub_brief`** — исследование до вопросов. Инструмент сам читает схему,
доменную модель, репозиторий и накопленные правила, а возвращает список
вопросов, ответов на которые нигде нет, и у каждого — первоисточник, откуда он
взялся. При включённом `automode` вместо вопроса возвращается умолчание,
которое будет применено.

**`dochub_lessons`** — правила, подтверждённые на прошлых схемах. Вызывать
первым, до вопросов: то, что уже записано, переспрашивать не нужно.

**`dochub_record_lessons`** — сохранить решения. Только после согласия
пользователя на публикацию; нужен `confirmed=true`.

### Схемы

**`dochub_parse_schema`** — элементы, связи и вложенность. Без `page`
дополнительно возвращает состав каждой страницы: в файле DrawIO часто лежит
несколько независимых диаграмм, и смешивать их нельзя. Логические диаграммы
отклоняются с объяснением.

**`dochub_render_schema`** — отрисовать исходную схему. PlantUML превращается в
SVG; DrawIO рисует движок превью, а `save_to` записывает картинку. С
`all_pages` каждая страница выгружается отдельным файлом.

**`dochub_ddd_tree`** — доменная схема компании: домены, ограниченные
контексты, поддомены, ответственные. По ней предлагается размещение схемы.

### Репозиторий

**`dochub_scan_repository`** — манифест: сколько компонентов, контекстов и
аспектов, какие корневые префиксы используются.

**`dochub_search_components`** — искать перед описанием любого чужого.
Нечёткое сравнение включено по умолчанию, поэтому дубль, записанный иначе,
всё равно находится. Параметр `queries` принимает сразу список: манифест
собирается один раз на всех, и минута поштучных запросов по настоящему
репозиторию превращается примерно в секунду.

**`dochub_locate_owner`** — чей это компонент и в какой файл он должен попасть.
Владение начинается с уровня сервиса: голый корень платформы ничем не владеет.

**`dochub_reconcile_with_code`** — сверяет схему с исходниками и перечисляет
расхождения с файлом и строкой. Сам ничего не решает: что включать — выбор
пользователя.

### Построение

**`dochub_draft_from_schema`** — структурный черновик. `own_root` обязателен:
не зная, какой сервис описывает схема, чужие компоненты уехали бы в ваш файл.
Всё вне этой рамки перечисляется отдельно.

### Проверка

**`dochub_validate_context`** — ссылочная целостность: неизвестные компоненты,
отсутствующие аспекты, связи за пределы контекста.

**`dochub_check_registration`** — подключён ли файл к дереву и объявлены ли
корневые платформы, родительские аспекты и внешние сервисы.

**`dochub_render_context`** — собирает PlantUML контекста метамоделью DocHub.
Полезно, чтобы убедиться, что контекст вообще рендерится.

**`dochub_preview`** — разделённый экран. Страница сама подхватывает правки
YAML; слева остаётся оригинал, справа результат. Выгрузить можно обе стороны —
оригинал в SVG, результат в YAML, PlantUML или SVG.

### Публикация

**`dochub_repo_sync`** — состояние архитектурного репозитория до начала
работы: доступен ли origin вообще, насколько отстала локальная копия, что не
закоммичено, и рабочая ветка. Обновление только fast-forward и пропускается,
если в каталоге есть несохранённое, — чужую работу инструмент не теряет.
Вызывать первым, а не последним: схема, собранная на устаревшей копии,
разойдётся с чужими правками, и выяснится это только при push.

**`dochub_register_schema`** — пишет в общие и чужие файлы. Без `apply`
возвращает только план; правки в чужих поддоменах помечены, чтобы агент
предупредил пользователя.

**`dochub_publish`** — ветка, коммит, push, merge request. Нужен
`confirmed=true` после явного согласия пользователя; единственное исключение —
`automode`: он публикует сам и пишет об этом в ответе. Сообщение коммита
собирается по шаблону из настроек — передавайте `schema_name`, а не
сочиняйте текст. Ветка назначения, ответственный, ревьюверы, squash и удаление
ветки тоже берутся из настроек, если не переданы параметрами. Мерж инструмент
не делает никогда.

**`dochub_changed_entities`** — что меняет ветка, для обоих репозиториев. Для
репозитория сервиса перечисляет изменённые файлы кода, чтобы ограничить схему
рамками задачи; для архитектурного — добавленные и изменённые компоненты,
аспекты и контексты, что удобно при ревью чужого merge request.

## Примеры

Что уже есть в репозитории:

```
dochub_scan_repository(manifest_path="<репозиторий>/architecture/dochub.yaml")
```

Есть ли компонент для чужого API:

```
dochub_search_components(manifest_path="...", query="catalogApi")
```

Где описывать новую очередь:

```
dochub_locate_owner(repo_root="...", component_ids=["dotnet.eventBus.myQueue"])
```

Сверить схему с исходниками:

```
dochub_reconcile_with_code(schema_path="service.drawio", project_root="<исходники>")
```

Показать результат и ждать замечаний:

```
dochub_preview(schema_path="service.drawio", yaml_path="<репозиторий>/.../поддомен.yaml")
```

## Прогнать весь путь без GitLab

Локальная папка заменяет репозиторий полностью — для git это тот же код вплоть
до `push` включительно:

```bash
git clone --bare <ваш клон арх.репозитория> origin.git
git clone origin.git work
```

Указываете `DOCHUB_REPO_ROOT` на `work` — и ветка, коммит и push проходят
по-настоящему, на настоящих данных, без доступа в корпоративную сеть.

Единственное, чего папка заменить не может, — **merge request**: это HTTP-вызов
к API GitLab, а у пути к папке нет хоста. `dochub_publish` так и говорит: ветка
ушла, merge request не создан, — вместо того чтобы собирать из пути
бессмысленный адрес.

## Настройки

Всё лежит в `.env` рядом с проектом; `.env.example` — образец с пояснениями.
Одноимённая переменная окружения перебивает файл, так что клиент может
переопределить одно значение, ничего не редактируя.

| Ключ | Что задаёт |
|---|---|
| `DOCHUB_REPO_ROOT` | архитектурный репозиторий |
| `DOCHUB_MANIFEST` | корневой `dochub.yaml`; выводится из репозитория, если не задан |
| `DOCHUB_DDD_PATH` | доменная схема компании |
| `DOCHUB_PROJECTS_ROOT` | где лежат репозитории сервисов |
| `GITLAB_TOKEN` | токен со scope `api` — только для создания merge request |
| `DOCHUB_REMOTE_PROTOCOL` | `https` или `ssh`: чего ждёт origin |
| `DOCHUB_TARGET_BRANCH` | ветка, в которую идёт merge request |
| `DOCHUB_BRANCH_PREFIX` | префикс рабочей ветки |
| `DOCHUB_COMMIT_TEMPLATE` | сообщение коммита; подставляется `{schema}` |
| `DOCHUB_MR_ASSIGNEE`, `DOCHUB_MR_REVIEWERS` | кто отвечает за MR и кто ревьюит |
| `DOCHUB_MR_SQUASH`, `DOCHUB_MR_REMOVE_SOURCE_BRANCH` | как сливается ветка |
| `DOCHUB_AUTOMODE` | агент доводит работу до merge request сам |
| `DRAWIO_PATH` | Draw.io Desktop, если нужна выгрузка в PNG или PDF |

`DOCHUB_ENV` указывает на другой `.env`, `DOCHUB_WORKSPACE` — на файл, куда
`dochub_workspace` сохраняет пути. `DOCHUB_TEST_REPO` нужен тестам, которым
требуется настоящий репозиторий.

Токен никогда не передаётся параметром инструмента и не попадает ни в лог,
ни в ответ.
